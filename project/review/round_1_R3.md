# Review round 1 — Reviewer 3 (clarity, reproducibility, journal fit, limitations)

Manuscript: "HoCo-kNN: training-free host-context nearest neighbours for benign-only NetFlow intrusion detection"
Target: J. King Saud Univ. – Computer and Information Sciences (Springer)

**Score: 5/10. Recommendation: major revision.**

## Summary of the submission
The authors take a raw 1-NN one-class detector that does poorly on NF-CSE-CIC-IDS2018-v2. They add two things: log rescaling of
min–max features, and the per-split mean of the log features over flows from the same source IP (a closed-form version of
E-GraphSAGE's one-hop aggregation). Under GDAE's protocol (8:1:1 random splits, five seeds, 0.3 % benign-validation FPR threshold)
the method gets higher PR-AUC than GDAE's reported numbers on both NetFlow-v2 datasets. Macro-F1 is higher on CIC-2018-v2 and lower on
UNSW-v2. Sections 7–8 analyse per-attack gains and how much of the gain comes from dedicated attacker hosts.

## Strengths
- The writing is unusually clear and honest. The weak result (UNSW Macro-F1) appears in the abstract, the results, the limitations
  and the conclusion. The testbed-inflation analysis (11.5 % of CIC test attack flows come from hosts seen in benign training;
  source-context-only reaches 0.9784) is the kind of self-critique the field needs.
- The plan really was frozen first. `experiments/plan_v5.yaml` was committed on 2026-11-26 12:56 UTC and the first HoCo-kNN test result
  on 13:06. The predictions P1–P3 in it match what is reported.
- Tables 2–5 are built by a script (`paper/build.py`) from the result JSONs. I checked a sample of numbers against the build logic and
  the abstract, text and tables agree (0.9299/0.9809 PR-AUC, 0.8783/0.9718 Macro-F1, 5.8 %/5.6 % → 100 % HOIC/LOIC-HTTP).
- The code is short and readable: data prep (44 lines), benchmark (89), method (58). The method itself is easy to re-implement.

## Concerns

### Journal fit and presentation

1. **MAJOR — No figures.** Every JKSU-CIS full text in the authors' own profile has 4–15 figures (GDAE has at least 9). Reviewers and
   editors at this journal expect at least:
   (a) a method overview diagram: flow table → log rescaling → group-by-source-host mean → concatenation → 1-NN distance to benign
       reference → benign-quantile threshold, with E-GraphSAGE's mean aggregation drawn next to it to make the "closed form of the
       first GNN layer" claim visual;
   (b) precision–recall curves (all seeds, or mean with a band) for HoCo-kNN, its ablations and the re-run baselines on both
       datasets;
   (c) a heatmap of per-attack detection rates (Table 5 as a figure), showing the HOIC/LOIC-HTTP jump and the Bot/Worms drops;
   (d) parameter sensitivity: PR-AUC and Macro-F1 against the log constant c, the reference size R and k;
   (e) Macro-F1/recall against the FPR budget (0.1 %–5 %). This would show whether the UNSW Macro-F1 gap is only about the operating
       point, which the paper currently asserts without showing;
   (f) a host-purity figure: the distribution of the attack share per source host in each dataset, which backs Section 7;
   optionally (g) runtime against PR-AUC for all methods.
   *What would resolve this:* add (a)–(f), all generated by scripts in the repository from existing result files where possible.
   (d) and (e) need cheap extra validation runs; (e) can be computed from stored scores if scores are saved.

2. **MAJOR — Far shorter and lighter than a JKSU-CIS method paper.** The manuscript is about 3,700 words with roughly 10 references.
   JKSU-CIS method papers are typically 8,000–12,000 words with 40–70 references, equation-numbered method sections, an algorithm box,
   complexity analysis, parameter sensitivity and a discussion section. Specifically missing:
   - numbered equations: min–max, φ, h(i), z(i), s(i), threshold;
   - pseudocode (Algorithm 1) for fitting and scoring;
   - time and memory complexity: O(|F|·d) for context, O(|Q|·R·d) for brute-force scoring, and memory for R = 200,000 × 82;
   - a parameter-sensitivity subsection;
   - a separate Discussion: deployment, when to prefer HoCo-kNN over GNNs, streaming variant, and evasion (an attacker who mixes in
     benign flows to dilute context, which Bot already illustrates).
   *What would resolve this:* expand Sections 4–7 along these lines, add a Discussion section, and grow the related work (see 3).

3. **MAJOR — References and related work are not in submittable form.**
   - The reference list carries internal repository paths ("details: literature/prior_art_v2/nfv2_oneclass.md").
   - GDAE is cited with no authors.
   - GraphIDS is "Guerra et al. (2026)" with no venue.
   - GIDS-Eval is "CCS 2026" with no authors or title.
   - The FlowGuard DOI (10.1922/comdem…) has an unusual prefix and must be checked.
   - Both inline citations and the list need Springer/JKSU style.
   - Related work leaves out what the paper's own argument rests on: kNN being strong on tabular one-class benchmarks (e.g. ADBench,
     Han et al. 2022), earlier kNN/LOF-based NIDS work, earlier host/aggregate flow features (e.g. CICFlowMeter-style windowed host
     statistics, Kitsune's damped per-host statistics), log/robust scaling of heavy-tailed flow features, and other NetFlow-v2 one-class
     or self-supervised work.
   - The unnumbered "Claim / prior work / difference" table is helpful, but it should be numbered (it is presumably the missing
     Table 1).
   *What would resolve this:* a complete, checked reference list (about 40 or more entries) in journal style; an expanded related work
   with a subsection on aggregated host features as prior art for "closed-form context"; Table 1 numbered.

4. **MINOR — Table and section numbering.** Tables start at 2. The runtime table has no number. Section 3 shows ablation numbers that
   only appear later (Table 3). *What would resolve this:* number all tables in order and give every table a caption.

### Reproducibility

5. **MAJOR — No README or exact reproduction commands, and no pinned environment.** The repository root has no README. It also has
   `MASTER_PROMPT.md`, `HANDOFF.md`, unrelated `figures/primary_by_arm.png` and `tables/E1_LODO...` left over from other topics, and a
   generic job runner (`run_all.py`). There is no `requirements.txt` or lock file. The paper names only "Python 3.13, scikit-learn,
   PyOD 3.6.9"; the environment has numpy 2.5.3, pandas 3.0.5 and scikit-learn 1.9.1. A reader cannot tell which entry points
   produce the paper.
   *What would resolve this:* a README (or `REPRODUCE.md`) with:
   - exact commands in order: `bash scripts/get_data_nfv2.sh`; `python src/nfv2_prep.py <DATA> <SEED>` (optional, called
     implicitly); `python src/nfv2_bench.py --data NF-UNSW-NB15-v2 --methods hc1_s,knn1,ck1_L,hc1_sd,hc1_d,hc1_os,iforest,hbos,pca --seeds 42,123,456,789,1234 --ref 200000`
     and the same for CIC (plus `knn5` on both); `python scripts/t3_per_attack.py`; `python scripts/t3_host_purity.py`;
     `python scripts/t3_report.py`; `python paper/build.py`;
   - a table mapping method codes (hc1_s = HoCo-kNN, ck1_L = log only, …) to paper names;
   - expected runtimes, RAM and disk: the CIC CSV is 18.9 M rows, and the parquet cache is a hidden step;
   - SHA-256 checksums of the downloaded zips (the script writes `.sha256` files, but their values are not published);
   - a pinned `requirements.txt`;
   - the validation-mode commands (`--eval val`) that produced the design decisions.
   The released repository should leave out unrelated topics and agent-orchestration files.

6. **MAJOR — The runtime table misreports HoCo-kNN's fit time as 0.0 s.** In `src/nfv2_bench.py` (`run`, the `hc` branch), the
   host-context computation for all three splits and `ref_subsample` (an `np.unique` over about 1.9 M × 82 rows plus seeded sampling)
   run *before* `t0 = time.time()`. So HoCo-kNN's "fit (s) = 0.0" leaves out exactly the work the raw kNN row counts (raw kNN's 5.7 s
   comes from `ref_subsample` inside `detector`, after `t0`). This flatters the method and makes the comparison unfair. "Training-free"
   is fine, but "fit 0.0 s" is not.
   *What would resolve this:* move the timer so that context and reference building are counted, re-time (one seed is enough), and
   report the context cost for each split separately. Also say that each job used one core; the abstract's "runs on a 4-core CPU" can
   be read as needing all 4.

7. **MINOR — The design-hygiene claim does not fully match the logs.**
   - Section 5 says the log constant was a design decision taken on validation. Every validation run in `results_t3_val/` uses
     c = 1e4: `Rep` and `context` have no switch for c, so no other value was tried.
   - Most validation runs used R = 50,000, not 200,000, and HoCo-kNN (`hc1_s`) was validated on CIC only at R = 50,000.
   - Variants that were explored and dropped (categorical one-hot `ck1_C`, `ck1_LCP`, dropping the source port `ck1_LP`, k = 10) are
     not reported.
   - "plan_v5" is cited in the text, but readers have no access to it.
   *What would resolve this:* state precisely what was tuned and what was fixed a priori. Report all validation runs in a supplementary
   table. Cite the frozen plan as a supplementary file with its commit timestamp. Either run a small c sweep or say that c was set a
   priori.

8. **MINOR — Ablation table has gaps that do not match the plan.** plan_v5 lists `knn5` among the reproduced baselines, but Table 3
   shows "—" for UNSW (k = 5, raw) and for the two context-only variants on UNSW.
   *What would resolve this:* run the missing four UNSW cells (cheap), or explain why they were left out.

9. **MINOR — Feature description.** Section 3 says "IP addresses and timestamps are removed", while Section 8 says "NetFlow-v2 carries
   no timestamps". Also, L4_SRC_PORT, an ephemeral per-flow value, is kept in the 41 features.
   *What would resolve this:* list the 41 features in an appendix table, remove the word "timestamps", and justify keeping the source
   port, or report the `ck1_LP` validation result.

### Clarity, consistency and claim calibration

10. **MAJOR — Some claims are stronger than the statistics support.**
    - The conclusion says HoCo-kNN "ranks attacks better than the published graph models". The intro says it became "the most accurate
      detector we evaluated".
    - But Table 4 shows that on UNSW-v2 the PR-AUC advantage over GraphIDS (Holm p = 0.062) and over the AE (p = 0.083) is not
      significant.
    - "Most accurate" holds only for PR-AUC: on UNSW, Macro-F1 ranks HoCo-kNN behind four methods.
    - The abstract's statement that raw kNN "already competes with" graph detectors on UNSW-v2 is generous: 0.7808 vs 0.8591 PR-AUC
      and 0.7438 vs 0.9491 Macro-F1.
    *What would resolve this:* qualify these sentences ("highest mean PR-AUC; significantly higher than GDAE and Anomal-E on both
    datasets, not significantly higher than GraphIDS/AE on UNSW-v2"). Replace "most accurate" with the specific metric. Soften
    "competes".

11. **MAJOR — Some limitations need fuller treatment.**
    The authors are commendably candid. Several issues still need more than a bullet point, because they decide whether the
    headline result says anything about a real network:
    - (a) **The source-IP context is close to an identity feature on CIC-2018-v2.** Attackers send about 93 % attack flows, and only
      11.5 % of attack test flows come from hosts seen in benign training. The detector can then flag "unknown host with unusual
      mean" more than "anomalous behaviour". Saying that GNNs do the same keeps the comparison fair, but it does not make the benchmark
      informative.
      *What would resolve this:* a host-disjoint evaluation (hold out source hosts) or a stratified report on attack flows from hosts
      that also send benign traffic in training, for HoCo-kNN and the per-flow variants.
    - (b) **Context is transductive and depends on split size.** Test context averages over the whole 10 % test split, including
      later flows and other attack flows from the same host. Training context averages over the 80 % benign-only split. A flow's
      context therefore depends on how many neighbours share the split, which a deployed detector does not control.
      *What would resolve this:* a sensitivity check that recomputes test context on random subsets (e.g. 10 %, 25 %, 50 % of the
      test split), to approximate smaller windows. If ordering is unavailable, state this as the main external-validity limitation in
      the abstract.
    - (c) **Evasion and dilution.** Bot detection drops from 100 % to 67 % because benign flows dilute the host context. An adaptive
      attacker can exploit this.
      *What would resolve this:* discuss it in a Discussion section.
    - (d) **Welch tests against reported numbers assume n = 5 independent runs on comparable splits.** GDAE's splits are not
      identical, even with the same seeds and protocol.
      *What would resolve this:* state this assumption next to Table 4, not only in Section 8.

12. **MINOR — The operating-point explanation for the UNSW Macro-F1 gap is asserted, not shown.** The paper says HoCo-kNN "ranks attacks
    better, but at our label-free 0.3 % operating point it recovers fewer". A threshold sweep or the oracle-best Macro-F1 (clearly
    labelled as not label-free) would show how much of the gap is threshold and how much is ranking. ROC-AUC and the realised test
    FPR are computed but not reported.
    *What would resolve this:* report ROC-AUC and test FPR in Table 2, plus the figure in 1(e).

13. **MINOR — Re-run baselines diverge more than "close to" suggests.** Our HBOS PR-AUC on UNSW is 0.5327 vs GDAE's 0.3214. Our
    iForest Macro-F1 is 0.4919 vs 0.6712. The Macro-F1 differences mostly come from different thresholds.
    *What would resolve this:* describe the divergence accurately and attribute it explicitly to the different threshold rules.

### Declarations and front matter

14. **MAJOR (administrative) — Declarations are placeholders.** JKSU-CIS (Springer) requires these sections: Funding; Competing
    interests; Ethics approval and consent (here "not applicable", public de-identified data); Data availability; Code availability
    with a working link (a placeholder is not enough for a reproducibility-centred paper); Author contributions (CRediT); and a
    statement on generative-AI use in preparing the manuscript, which the journal policy requires when it applies. The data-availability
    statement should name the UQ RDM DOIs and the licence or citation terms.
    *What would resolve this:* complete all declarations, add a public, archived code link (e.g. GitHub plus a Zenodo DOI), and add
    the AI-use statement.

15. **MINOR — Highlights.** The first highlight is 89 characters. Elsevier/JKSU-style highlights are limited to 85 characters including
    spaces. *What would resolve this:* shorten it (e.g. "Training-free nearest-neighbour detector for benign-only NetFlow IDS").

16. **MINOR — Title and abstract.** At about 300 words the abstract is near or over the usual 250-word limit, and it contains much
    narrative ("We asked how much…"). JKSU abstracts usually follow problem → method → results with % improvement → significance.
    *What would resolve this:* tighten to 250 words or fewer. Keep the honest Macro-F1 sentence and the testbed caveat.

## Overall assessment
The paper is honest, internally consistent and technically simple, and its central message is useful for this journal's readers: much
of what one-class GNN NIDS gain on NetFlow-v2 can be obtained from a closed-form host mean plus 1-NN. In its present form, though, it
does not look like a JKSU-CIS method paper. It has no figures, is very short, and has a thin and partly unformatted reference list. The
repository is close to reproducible, but it has no README, no pinned environment and a timing bug that understates HoCo-kNN's cost. The
two most important scientific additions are a host-disjoint (or host-overlap-stratified) evaluation and a context-window sensitivity
check. They would turn the candid limitations of Section 8 into evidence. With these additions I would expect to move to minor
revision.
